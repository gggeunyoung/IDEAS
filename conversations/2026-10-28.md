# 2026-10-28 대화 기록

## 사용자 의도
- Vercel Hobby 팀 정지 원인이 IDEAS 호출량인지 확인하고, Pro도 무제한이 아니므로 불필요한 조회를 반드시 줄이길 요청했다.

## 확인한 사실과 에이전트 제안
- Vercel 팀 사용량에서 Blob Simple Operations 11,392/10,000 초과를 확인했다. 함수 호출·CPU·전송량은 해당 한도 안이었다.
- 코드에서 유휴 상태에도 맥이 30초마다 Vercel 경유 health를 요청하고 주소 캐시는 20초뿐인 구조를 확인했다. 모델 추론 비용과 다른 저장소 읽기 문제다.
- 유휴 경유 조회 제거, 주소 캐시·동시 조회 병합, 장애 백오프, 화면 비활성 시 결과 조회 중지를 적용한다.

## 구현 및 확정된 결정
- 정상 유휴 점검은 터널을 직접 확인한다. Vercel 경유 확인은 주소 등록과 워커 인스턴스 변경 시만 수행한다. 등록 실패는 30초부터 최대30분 지수 백오프이며 맥 작업은 유지한다.
- 주소 캐시를 인스턴스별5분으로 늘리고 동시 저장소 조회를 합친다. 저장소 장애/강제 갱신은 30초 간격으로 제한한다. GET은 장애 시 주소 변경에 한해 재시도하고 POST는 중복 실행을 막기 위해 자동 재전송하지 않는다. 인증·사용자 응답은 캐시하지 않는다.
- 회의 상태 조회는 3초부터 새 내용이 없으면6→12→15초로 늘린다. heartbeat는 새 활동으로 계산하지 않는다. 숨겨진 탭에서는 조회하지 않고 다시 보이면 즉시 재개한다. 원격 AI 작업은 계속 진행된다.

## 검증
- 자동 검사129개 중128개 통과, 플랫폼별1개 생략. 24시간 정상 유휴 시뮬레이션에서 초기 등록 이후 Vercel 추가 요청0회 확인.
- 장애 백오프, 워커 교체 시 재등록, 동시 주소 조회 병합, 늦은 저장소 응답과 재등록 경합, 인증 없는 강제 갱신 거절, POST 중복 재전송 방지, 숨김/복귀 타이머와 로컬 JS 제공을 검사했다.
- 진행 중인 원격 작업이 없는 것을 확인한 뒤 맥 서비스를 재시작했다. 워커 인스턴스 변경과 새 polling.js HTTP200을 확인했다.

## 미해결 질문과 다음 행동
- 공개 운영 배포를 반영하고 실제 주소·로그인 설정의 응답을 확인한다. 팀 정지가 남아 있으면 운영 배포는 해제 이후에만 가능하다.
- 콜드 스타트와 실제 사용자 접속은 여전히 Blob 읽기를 발생시킨다. 이 변경을 전체 비용0 또는 기존 한도 초과 자동 해제로 설명하지 않는다.
