# IDEAS의 구조와 작업 흐름

## 목표와 완료 조건

사용자가 어느 기기에서든 회의실 웹에 질문하면, 켜져 있는 맥의 GPT·Claude CLI가 해당 프로젝트에서 작업하고 결과와 진행 상황을 웹으로 돌려준다. 회의실 프로그램의 저장소와 각 프로젝트의 작업 저장소는 분리한다. 구독 로그인으로 CLI를 호출하는 방식이며 맥 앱 화면을 클릭하는 방식은 아니다.

이번 변경의 완료 조건은 협업·사용자 이해 규칙의 기본 전달, 두 초기 접근법의 분리 수집, 이해 문서 누락 시 완료 차단, 웹에서 이해 가이드 읽기·다운로드다. 이 조건은 두 에이전트가 단독보다 우수하다거나 사용자가 이미 이해했다는 증거는 아니다.

## 구조와 데이터 흐름

주요 구성요소와 역할은 다음과 같다.

- `public/index.html`, `public/app.js`: 방 선택, 로그인, 질문 제출, 진행 상태, 답변과 파일 결과 표시. 화면의 설정과 대화는 작업 요청으로 변환한다.
- `api/remote.js`, `remote-proxy.mjs`: Vercel의 요청을 인증된 맥 워커 연결로 중계한다. Vercel에서 에이전트 프로세스를 실행하지 않는다.
- `remote-worker.mjs`: 로그인 세션을 검사하고 작업 ID·상태·이벤트를 맥에 보관한다. 웹을 닫아도 이미 접수된 작업은 맥에서 진행한다.
- `server.mjs`, `room-registry.mjs`: 방 ID를 등록된 저장소 경로로 해석하고 현재 방의 자료·회의·결과를 처리한다. 웹 입력으로 임의 PC 경로를 지정하는 구조가 아니다.
- `room.mjs`: 참가자·모드·예산을 검증하고 자율 협업, 토론, 파일 협업 등 실행 방식으로 전달한다.
- `team-workflow.mjs`: 자율 협업의 차례·세션·예산·진행 기록·완료 판단을 관리한다.
- `local-agents.mjs`: 계정의 CLI 실행 파일을 호출하고 도구 권한·모델 설정·응답을 처리한다. 모델의 추론은 제공자 서비스에서 수행한다.
- `collaboration-policy.mjs`: 기본 협업/이해 지침과 이해 문서의 형식 검사·공유용 읽기를 담당한다.
- `git-sync.mjs`, `deliverables.mjs`: 안전한 팀 파일의 Git 저장과 웹에서 읽을 별도 파일 공유본을 담당한다.

화면은 대화 읽기를 기본으로 한다. 하단의 “의견 쓰기”를 누르면 입력 패널이 펼쳐지고, 접기 또는 Esc로 닫아도 초안이 유지된다. 입력 패널은 대화 영역과 세로 공간을 나누며 답변을 덮지 않는다. 중단 버튼은 패널 밖에 있어 접힌 상태에서도 실행 중인 작업을 중단할 수 있다. UI 파일은 로컬 서버가 요청마다 읽고 Vercel은 정적 빌드로 배포하므로, 이번 UI 변경만을 위해 맥 워커를 재시작할 필요는 없다.

질문 → 브라우저 → Vercel 중계 → 맥 워커의 작업 접수 → 로컬 서버의 방 선택 → 팀 실행기 → GPT/Claude CLI → 프로젝트 파일·검증 → 진행 이벤트·답변·공유본 → 브라우저 순서다. 로컬 주소로 접속하면 Vercel 중계 단계 없이 로컬 서버를 사용한다.

## 핵심 로직

새 팀은 원래 저장소의 시작 커밋에서 전용 Git 작업 트리를 만든다. 작업 트리는 같은 저장소의 다른 브랜치를 별도 폴더에서 편집하는 기능이다. 사용자의 원래 체크아웃을 바꾸지 않고 `.ideas/team/<ID>/workspace`와 `ideas/team-<ID>`에서 작업한다.

첫 두 차례는 서로의 이번 답을 전달하지 않는 읽기 전용 접근법이다. GPT에는 읽기 전용 샌드박스를 사용하고, Claude에는 읽기 도구만 제공한다. 이때 기존 구현 세션을 재개하거나 추가 쓰기 폴더를 제공하지 않는다. 접근법 두 개가 모이면 두 사람에게 공유하고 새 쓰기 세션에서 교대 구현·검증을 시작한다. 이후 같은 에이전트는 자신의 작업 세션을 이어간다.

예를 들어 “검색 결과 중복 제거” 요청이면 두 사람이 각각 중복의 정의·식별 키·검사 방법을 제안한다. 구현 차례에는 둘의 안을 비교해 정규화 URL 등 실제 기준을 선택한다. 다른 사람은 URL 변형, 빈 값, 중복 수집 같은 반례를 확인하고 선택 이유를 이해 가이드에 남긴다. 이 예시는 특정 위키레이더 요구사항을 확정한 것은 아니다.

완료는 서로 다른 사람의 연속 완료 제안과 기존 검증 조건을 확인한다. 이해 가이드의 필수 제목과 본문이 빠지면 완료 합의를 허용하지 않는다. 파일 존재와 형식을 검사하는 것이므로 테스트의 적절성·사실 정확성까지 실행기가 증명하지는 않는다. 예산 종료, 반복 정체, 사용자 결정 필요, 실행 실패를 완료와 구분한다.

## 설계 선택과 대안

공통 규칙을 브라우저 설정값이 아니라 서버 프롬프트에 넣어 기기가 달라도 적용한다. 반면 목표·완료 조건은 사용자의 실제 요청에서 구체화한다. 임의의 고정 목표를 모든 방에 넣지 않는다.

교대 쓰기는 같은 파일의 동시 수정 충돌을 피하고 검토 대상을 명확히 한다. 대안은 에이전트별 작업 트리에서 병렬 수정 후 병합하는 방식이다. 더 빠를 수 있지만 변경 충돌과 병합 검증을 추가로 관리해야 한다. 현재는 처음부터 이 복잡도를 늘리지 않는다.

초기 접근법은 서로 분리하지만 기존 코드와 선택 자료는 공통 배경이다. 완전히 독립적인 판단을 보장하지 않는다. 두 모델이 동의한 사실도 외부 기준으로 검증해야 한다.

이해 문서는 프로젝트 브랜치에 보존하고 웹 공유본도 만든다. 브랜치를 병합하기 전에도 웹에서 설명을 읽을 수 있다. 공유본은 비밀정보·크기 검사를 통과해야 하며 원본 파일과 별도의 저장본이다.

## 실행과 검증

개발 확인은 저장소 루트에서 실행한다.

```sh
npm test
npm run build:static
npm start
```

운영 맥 서비스가 이미 같은 포트를 사용 중이라면 개발 서버를 중복 시작하지 않는다. 서비스 상태는 `npm run service:status`로 확인한다. 다른 기기의 공개 접속에는 맥 서비스·터널·인터넷 연결이 유지되어야 한다.

자동 검사는 실제 모델 대신 모의 응답을 사용하는 경우가 많다. 초기 제안의 전달 분리, 읽기 전용 CLI 인자, 세션 전환, 완료 차단, 파일 공유와 기존 인증·중계·저장 기능을 검사한다. 실제 GPT·Claude 실행 결과는 날짜별 대화 기록의 검증 절을 확인한다. 자동 검사 통과가 실제 모델의 모든 행동을 보장하지 않는다.

## 한계와 다음 단계

맥이 잠들거나 종료되면 에이전트 작업을 계속할 수 없다. 네트워크 단절이나 계정 사용량 한도도 중단 원인이 된다. 기존 앱의 다른 채팅 기억·플러그인·GUI 제어가 회의실에 자동 연결되는 것은 아니다.

새 팀의 초기 두 차례도 전체 예산에서 사용한다. 리서치 최소 예산은 초기 계획2+작업6을 고려한 8차례이며, 수정·최종 검토가 남으면 더 필요하다. 현재 예산은 시간과 차례 수이며 구독의 남은 한도를 정확히 알고 자동 할당하지 않는다.

다음 검증은 동일한 자원에서 GPT 단독·Claude 단독·협업을 비교하는 것이다. 사용자 이해도도 “설명을 제공했다”와 “사용자가 흐름을 설명하고 수정해 봤다”를 구분해야 한다.

## 직접 확인할 질문

- Vercel이 켜져 있어도 맥이 꺼지면 왜 작업할 수 없을까? 모델을 호출하고 파일을 수정하는 프로세스가 맥에 있기 때문이다.
- 두 에이전트가 같은 프로젝트를 다뤄도 왜 동시에 파일을 덮어쓰지 않을까? 팀 실행기가 차례로 호출하기 때문이다.
- 팀 브랜치에 파일이 있는데 원래 폴더에는 왜 안 보일까? 별도 작업 트리에 저장하며 원래 브랜치에 자동 병합하지 않기 때문이다.
- 작은 개발 실습: `collaboration-policy.mjs`의 설명 원칙에 원하는 보고 예시 한 문장을 추가하고 `npm test`를 실행한다. 다음 실행에 적용하려면 서버의 새 프로세스가 수정된 모듈을 읽어야 한다. 운영에 반영하려면 진행 작업을 확인하고 검증된 변경만 커밋·배포·재시작한다.
- 확인 실습: 새 팀을 제한된 예산으로 시작하고 첫 두 답변이 “독립 접근법”으로 표시되는지 본다. 종료 뒤 “파일·결과”에서 이해 가이드를 열어 실제 구현의 입력 하나가 어떤 경로를 거쳐 출력되는지 설명해 본다.
