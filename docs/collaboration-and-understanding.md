# 기본 협업과 프로젝트 이해

회의실의 목적은 두 에이전트가 결과물을 함께 만들고, 사용자가 그 구조와 로직을 이해하여 설명·수정할 수 있게 하는 것이다. 이 규칙은 사용자 메시지에 매번 붙이지 않아도 서버 프롬프트에 기본 적용한다. 구현은 `collaboration-policy.mjs`에 모은다.

## 실행 순서

1. 새 팀은 GPT와 Claude의 접근법·위험·완료 조건·검증 방법을 각각 수집한다. 순차 호출하지만 두 번째 호출에는 첫 번째 결과를 전달하지 않는다. 동일한 작업 트리를 읽기 전용으로 보고, 기존 CLI 세션도 재개하지 않는다. 선택한 자료와 기존 저장소 내용은 공통 배경이므로 완전히 아무런 영향이 없는 판단을 보장하는 것은 아니다.
2. 두 제안이 모이면 공유하고 가장 작은 실행 가능한 결과부터 만든다. 초기 읽기 전용 세션을 쓰기 세션으로 전환하지 않고 새 작업 세션을 시작한다. 구현·검증 역할은 작업에 맞게 정하며 모델별 고정 우열을 가정하지 않는다.
3. 한 차례에 한 명만 파일을 수정한다. 다른 사람은 실제 결과를 읽고 누락·반례·실패 경로를 검증한다. 문제·재현 근거·영향·수정 제안으로 의견을 남기고 테스트·실험·출처로 이견을 해결한다.
4. 중요한 설계·구현 변경 뒤 `docs/PROJECT_GUIDE.md`를 갱신한다. 상대가 코드·근거와 설명이 맞는지 직접 확인하도록 지시한다. 종료 때 파일·결과에서 읽고 내려받을 수 있도록 별도 공유본을 만들며, 웹 공유를 위해 핵심 설명은 16,000자 이내로 정리한다.
5. 예산 안에서 작업을 계속하고, 완료 조건을 확인하면 서로 완료를 제안한다. 이해 가이드의 필수 설명이 비어 있으면 실행기는 완료 합의를 허용하지 않는다. 실제 장애·예산 도달·사용자 결정 필요는 완료와 구분한다.

독립 접근법 두 번도 기존 시간·차례 예산에 포함하며 추가로 무제한 호출하지 않는다. 새 팀에 2차례만 주면 접근법 수집만 하고 예산 종료할 수 있다. 웹 UI는 4차례 이상을 제공한다. 리서치는 초기 2차례와 작업 최소 6차례를 고려해 최소 예산 8차례를 요구한다. 두 사람의 최종 교차 확인이나 수정이 남으면 더 많은 예산이 필요하다. 기존 팀을 계속할 때는 이미 수집한 초기 접근법을 재사용한다. 구버전 팀은 최초 적용 시 기존 작업물을 보존하고 접근법 수집과 CLI 세션을 새로 시작한다.

## 이해 가이드에 담을 것

프로젝트 팀 브랜치의 `docs/PROJECT_GUIDE.md`는 다음 제목과 구체적인 설명을 담는다.

- `목표와 완료 조건`: 사용자가 할 수 있게 되는 일과 확인할 기준.
- `구조와 데이터 흐름`: 구성요소의 역할, 실제 파일, 입력부터 저장·출력까지의 흐름.
- `핵심 로직`: 주요 함수·알고리즘·분기와 실제 입력/출력 예시.
- `설계 선택과 대안`: 채택한 이유, 다른 방법, 단점, 변경의 영향.
- `실행과 검증`: 실행 명령, 실제 확인한 결과, 확인하지 않은 범위.
- `한계와 다음 단계`: 알려진 문제, 가정, 현장 검증이나 남은 결정.
- `직접 확인할 질문`: 사용자가 자기 말로 설명할 질문, 직접 해볼 작은 변경, 예상 결과.

기획·리서치 프로젝트에서는 없는 프로그램 구조를 꾸며내지 않는다. 문제 구조, 자료에서 판단으로 이어지는 논리, 대안과 검증 방법을 설명한다. 토론·파일 협업·구형 목표 실행에도 이해 원칙을 전달하지만, 프로젝트 파일을 직접 다루는 자율 협업만 이 가이드 파일을 완료 조건으로 검사한다.

사용자가 매 차례 설명을 승인하거나 시험에 답해야 다음 작업이 진행되는 방식은 아니다. 가능한 작업을 진행하면서 설명을 남긴다. 실행기가 검사하는 것은 파일 위치·제목·본문의 존재와 크기뿐이며, 사실 정확성·코드 일치·사용자의 이해를 증명하지 않는다. 설명이 어려우면 사용자는 회의실에 “이 흐름을 작은 입력 하나로 단계별 설명해줘” 또는 “이 조건을 바꾸면 어디가 달라지는지 같이 확인해줘”라고 이어갈 수 있다.

## 결과의 우수성은 별도로 평가

이 운영 규칙을 적용했다는 사실은 단독 에이전트보다 우수하다는 증거가 아니다. GPT 단독·Claude 단독·GPT+Claude를 같은 시작 커밋·도구·자료·전체 예산으로 비교하고, 외부 인수 기준으로 평가해야 한다. 단독 에이전트에도 자기 검토와 수정 기회를 준다. 실제 사용성, 결함, 시간·사용량, 사용자 개입, 검토가 발견하고 수정한 문제를 기록한다. 반복 실험과 새로운 과제에서 결과가 유지되는지 확인하기 전에는 일반적인 우월성을 주장하지 않는다.
